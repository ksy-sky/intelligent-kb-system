# Интеллектуальная обучающая система по дисциплине «ПиОИвИС»

Проект интеллектуальной обучающей системы (ИОС) по дисциплине **«Представление и обработка информации в интеллектуальных системах» (ПиОИвИС)**, БГУИР. Система состоит из трёх частей:

1. **База знаний** (4 семестр) — 376 концептов в 12 JSON-файлах, онтологический формализм с типизированными связями.
2. **Подсистема решателей задач** (5 семестр) — детерминированные алгоритмы на графе знаний: диагностика пробелов, учебная траектория, сравнение понятий, проверка БЗ, аналитика группы. Все обращения к ним проходят через единый маршрутизатор `SolverRouter`.
3. **Интерфейсы** — консольное меню (`main.py`) и веб-приложение на Streamlit (`app.py`).

Решатели не используют статистические и обучаемые модели: одинаковые входные данные при неизменной БЗ всегда дают одинаковый результат, а каждый результат сопровождается объяснением.

## Сценарии использования

| № | Сценарий | Роль | Модуль |
|---|----------|------|--------|
| 1 | Самостоятельное изучение теории: навигация по разделам и карточки понятий | студент | `scenario_study.py` |
| 2 | Глоссарий: точный и нечёткий поиск терминов | студент | `scenario_glossary.py` |
| 3 | Интеллектуальный ассистент на базе LLM (Ollama) | студент | `scenario_assistant.py` |
| 4 | Адаптивная диагностика пробелов | студент | `solver_diagnostics.py` |
| 5 | Учебная траектория и рекомендации | студент | `solver_trajectory.py` |
| 6 | Сравнение двух понятий | студент | `solver_comparator.py` |
| 7 | Проверка целостности базы знаний | преподаватель | `solver_admin.py` |
| 8 | Аналитика успеваемости и групповые пробелы | преподаватель | `solver_analytics.py` |

### Сценарий 4. Диагностика пробелов
Студент выбирает целевой концепт (например, «OWL»). Решатель находит его пререквизиты по связям «надкласс» и «используется в», задаёт проверочные вопросы и по ответам определяет пробелы. Работает в два шага: первый запрос возвращает вопросы (`status = need_input`), второй — с ответами — пробелы. Итог сохраняется для аналитики (см. [хранение результатов](#хранение-результатов-диагностики)).

### Сценарий 5. Траектория и рекомендации
По набору пробелов (и необязательной цели) строится граф зависимостей, пробелы упорядочиваются топологической сортировкой (алгоритм Кана, порядок детерминирован), рассчитывается критичность каждого понятия. К каждому шагу подбираются определение, примеры, связи и номера лабораторных работ; для понятий без явных связей применяется запасной TF-IDF-поиск похожих.

### Сценарий 6. Сравнение понятий
Для двух понятий находится ближайший общий предок (LCA) в иерархии «надкласс», строятся пути до него и матрица общих и уникальных свойств.

### Сценарий 7. Проверка базы знаний
Преподаватель правит JSON-файлы в `data/` и запускает проверку: уникальность `concept_id`, обязательные поля, ссылочная целостность связей, ацикличность иерархии «надкласс». Результат — сообщение об успехе со статистикой либо код `VALIDATION_FAILED` со списком нарушений. Рабочая БЗ при этом не меняется.

### Сценарий 8. Аналитика группы
По результатам диагностики студентов считается доля студентов с пробелом по каждому проверявшемуся концепту; концепты с долей не ниже порога θ выводятся по убыванию доли. Учитывается последняя попытка каждого студента.

## Архитектура

```
Интерфейс (консоль main.py / Streamlit app.py)
        │  запрос {"action": ..., "params": {...}}
        ▼
   SolverRouter  — проверка запроса, нормализация (ID / термин → concept_id),
        │          вызов решателя, единый формат ответа
        ▼
   Решатели сц. 4–8  ──►  KnowledgeBaseLoader  ──►  data/*.json
                            (индексы в памяти)
```

Принципы:
- **База знаний отделена от кода.** Знания хранятся в JSON; правка БЗ не требует изменения программы.
- **Единственный доступ к знаниям — `KnowledgeBaseLoader`.** Решатели не читают файлы и не знают друг о друге.
- **Единая точка входа — `SolverRouter`.** Интерфейсы обращаются к решателям 4–8 только через него.
- **Сбой одного решателя не ломает остальные:** решатели подключаются в роутере по одному, неработающий модуль отключает только свой сценарий (в ответ попадает предупреждение).

## Установка и запуск

Требуется Python 3.9+.

```bash
git clone https://github.com/ksy-sky/intelligent-kb-system.git
cd intelligent-kb-system
pip install -r requirements.txt
```

### Веб-интерфейс (Streamlit)

```bash
streamlit run app.py
```

Приложение откроется в браузере (по умолчанию `http://localhost:8501`). Роль выбирается в боковой панели: у «Студента» доступны диагностика, план изучения и сравнение понятий, у «Преподавателя» дополнительно — проверка БЗ и аналитика группы. Выбор роли — демонстрационный, авторизации нет.

Чтобы получить данные для аналитики, пройдите диагностику за нескольких «студентов» (разные имена) по одной и той же цели, затем откройте «Аналитика группы».

### Консоль

```bash
python main.py
```

```
  1 — Изучение теоретического материала
  2 — Глоссарий (поиск термина)
  3 — Интеллектуальный ассистент
  4 — Диагностика пробелов
  5 — Траектория и рекомендации
  6 — Сравнение понятий
  7 — Проверка базы знаний
  8 — Аналитика группы
  q — Выход
```

### Ассистент (сценарий 3, необязательно)

Для сценария 3 нужен локальный [Ollama](https://ollama.com) с моделью `llama3.2`:

```bash
ollama pull llama3.2
ollama serve        # в отдельном терминале
```

Без Ollama ассистент переключается на локальный поиск по БЗ. Остальные сценарии от Ollama не зависят.

## API маршрутизатора

Все обращения к решателям сценариев 4–8 выполняются одним вызовом:

```python
from src.kb_loader import KnowledgeBaseLoader
from src.solver_router import SolverRouter

loader = KnowledgeBaseLoader(KB_FILES); loader.load()   # KB_FILES — список файлов из main.py
router = SolverRouter(loader)

resp = router.handle_request({"action": "plan", "params": {"gaps": ["RDF", "OWL"]}})
```

Понятия в параметрах можно задавать **идентификатором** (`CL158`) или **термином** (`RDF`) — роутер приведёт их к `concept_id`.

### Действия и параметры

| action | Сценарий | Параметры |
|--------|:---:|-----------|
| `diagnose` | 4 | `target` — цель; `answers` — необязательно, ответы `{concept_id: ответ}` |
| `plan` | 5 | `gaps` — список пробелов; `target` — необязательная цель |
| `compare` | 6 | `concept_1`, `concept_2` |
| `admin` | 7 | — |
| `analytics` | 8 | `student_models` — список наборов `concept_id`; `target_concepts` — список; `threshold` — число 0…1 (по умолчанию 0,5) |

### Формат ответа

```json
{
  "status": "success | need_input | error",
  "action": "plan",
  "data": { },
  "explanation": { "summary": "…", "used_concepts": ["C001", "…"] },
  "error": null,
  "metadata": { "elapsed_ms": 0.7, "warnings": [] }
}
```

При ошибке `status = "error"`, `data` пуст, а `error` содержит `{code, message, details}`.

### Коды ошибок

| Код | Причина |
|-----|---------|
| `UNKNOWN_ACTION` | неизвестное действие |
| `MISSING_PARAM` | не передан обязательный параметр |
| `BAD_PARAM_TYPE`, `BAD_PARAM_VALUE` | неверный тип или значение параметра |
| `BAD_ID_FORMAT` | значение похоже на идентификатор, но формат неверный |
| `CONCEPT_NOT_FOUND` | концепт не найден; в `details.similar` — похожие термины |
| `AMBIGUOUS_CONCEPT` | термину соответствует несколько концептов; в `details.candidates` — варианты (тема, источник, начало определения) |
| `CYCLE_DETECTED` | цикл в иерархии при построении траектории |
| `COMPARE_FAILED` | не удалось сравнить понятия |
| `VALIDATION_FAILED` | проверка БЗ нашла нарушения (в `details` — список) |
| `CRITICAL_ERROR`, `DIR_NOT_FOUND`, `NO_FILES` | ошибка загрузки БЗ: повреждённый JSON, нет каталога или файлов |

## Структура базы знаний

База хранится в 12 JSON-файлах каталога `data/`. Каждый файл содержит массив `topics`, тема — массив `concepts`.

```json
{
  "concept_id": "C042",
  "term": "онтология",
  "topic_id": "T07",
  "definition": "Явная спецификация концептуализации",
  "examples": ["Ontology Web Language (OWL)", "Protégé Editor"],
  "relations": {
    "надкласс": ["C040"],
    "используется в": ["Semantic Web", "Интеграция данных"],
    "разбиение": ["Таксономии", "Аксиомы", "Индивиды"]
  }
}
```

| Поле | Обязательное | Описание |
|------|:---:|----------|
| `concept_id` | да | уникальный идентификатор: `C001…` (теория), `CL001…` (лабораторные) |
| `term` | да | название понятия |
| `topic_id` | да | раздел: `T01…T07` (лекции), `L01…L05` (лабораторные) |
| `definition` | нет | текстовое определение |
| `examples` | нет | массив примеров |
| `relations` | нет | словарь «тип связи → массив значений»; значение — `concept_id` либо текстовое пояснение |

Типы связей: `надкласс` (формирует таксономию), `разбиение`, `составные части`, `используется в`, `противопоставляется`, `пояснение`.

### Загрузчик и валидатор

`KnowledgeBaseLoader.load()` объединяет файлы, проверяет их `kb_validator`, строит индексы:
- `concepts_by_id` — доступ к концепту по идентификатору за O(1);
- `concepts_by_term` — регистронезависимый поиск по термину (допускает омонимы);
- `topics_index` — разделы и их концепты.

Методы: `get_concept`, `search_by_term`, `resolve_relations`, `get_related_labs`.

Валидатор прерывает загрузку (исключение `KBValidationError`) при дубликате `concept_id`, нарушении схемы и цикле в иерархии «надкласс». Ссылка на несуществующий идентификатор даёт предупреждение без прерывания.

## Хранение результатов диагностики

Результаты сценария 4 дописываются в файл `data/results/diagnostics.jsonl` (одна строка — один JSON):

```json
{"student": "Иван", "time": "2026-11-26T14:20:05", "target_id": "CL152",
 "prerequisites": ["CL158", "CL175"], "mastered": ["CL158"], "gaps": ["CL175"], "unanswered": []}
```

Модуль `results_store.py`: `save_diagnostic` (запись), `load_latest` (последняя запись каждого студента по цели), `list_targets` (цели, по которым есть данные), `to_analytics_params` (преобразование в параметры действия `analytics`). Каталог `data/results/` добавлен в `.gitignore`: это рабочие данные, а не часть БЗ.

## Тестирование

```bash
python -m unittest discover -s tests -v
```

Всего 327 тестов: валидатор и загрузчик, сценарии 1–3, решатели 4–8 напрямую и через роутер, граничные и ошибочные случаи. Тесты решателей используют небольшую тестовую БЗ `tests/kb_fixtures.py`, а не реальные файлы.

Примечание: тест `test_available` в `test_scenario_assistant.py` проверяет доступность Ollama и падает на машине, где Ollama не запущен; это ожидаемо и не связано с решателями.

## Расширение базы знаний

1. Откройте нужный файл в `data/` (например, `glossary_T07.json`) и добавьте объект в массив `concepts`:
   ```json
   {
     "concept_id": "C168",
     "term": "мета-онтология",
     "topic_id": "T07",
     "definition": "Онтология, описывающая структуру и семантику других онтологий",
     "relations": { "надкласс": ["C042"] }
   }
   ```
2. Запустите проверку: страница «Проверка БЗ» в веб-интерфейсе, пункт 7 консольного меню или
   ```bash
   python -c "from main import KB_FILES; from src.kb_loader import KnowledgeBaseLoader as L; print(L(KB_FILES).load())"
   ```
3. Перезапустите приложение, чтобы изменения попали в индексы.

Рекомендации по правке БЗ:
- Не меняйте `concept_id` существующих понятий и не удаляйте понятия, на которые есть ссылки: ссылки перестанут работать (проверка БЗ сообщит о них предупреждением).
- Определения и примеры можно менять в любое время.

## Ограничения

- Решатели работают только с понятиями из БЗ; запросы на естественном языке (кроме сценария 3) не разбираются.
- Нормализация терминов — по точному совпадению; синонимы и словоформы не распознаются, при опечатке предлагаются похожие термины.
- Качество результатов зависит от полноты БЗ (у части концептов нет определения или связей).
- Аналитика использует последнюю попытку каждого студента, без истории.
- Хранилище результатов — файл JSONL, не рассчитан на одновременную запись.
- Построение траектории поддерживает не более одной цели; при цикле в иерархии возвращается ошибка без частичного плана.
- Роль в веб-интерфейсе выбирается переключателем без авторизации.
